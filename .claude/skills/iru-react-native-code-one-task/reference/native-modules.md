# Native modules and components

Read when the task adds or changes native code, a Codegen spec, an Expo module, or a config plugin. Native code is
the most expensive part of a React Native app to get wrong — it compiles separately per platform, can't be
OTA-updated, and crashes the process instead of throwing a JS error — so the first question is always whether it is
needed at all.

## Is native code legitimate here?

In order — stop at the first that covers the task:

1. **A JS/TS API** of React Native or an already-installed library (`Linking`, `AppState`, `Share`,
   `PermissionsAndroid`, `expo-*` SDK module, …).
2. **A configuration change**: expo → `app.json`/`app.config.*` field or a package's config plugin (`expo.md`);
   metro → `Info.plist`/`AndroidManifest.xml`/Gradle/Podfile edit (`metro.md`).
3. **A maintained third-party native library** — a new dependency, so only if the task asks for it (otherwise a
   blocker to report).
4. **Custom native code**, written by this task — only when the task explicitly calls for it, or when 1–3 are
   genuinely exhausted *and* the task's text makes native work its scope.

| Toolchain | Where custom native code goes | Never |
|---|---|---|
| **expo** | A **local Expo module** (`modules/<name>/`, created with `npx create-expo-module@latest --local`) using the Expo Modules API, plus a config plugin when it needs native config. | Code under `android/`/`ios/` (generated by prebuild — lost on the next run). |
| **metro** | A **Turbo Module** (functions/constants) or **Fabric native component** (views) with a Codegen spec in TS and implementations in `android/` (Kotlin) and `ios/` (Obj-C++, optionally calling Swift). An Expo module is also possible if `expo-modules-core` is already installed (`npx install-expo-modules`) — don't add it for one task. | A legacy bridge module (`RCT_EXPORT_MODULE` without a spec, `ReactContextBaseJavaModule` without a generated `Native…Spec`) — the legacy architecture is gone in RN 0.82+. |

Both platforms, always: a module implemented for one platform only must still exist on the other (throwing a clear
`Error` / rejecting with a documented code, or `Platform.OS`-guarded in JS) — never `undefined` at runtime.

## Turbo Module (metro) — spec first

1. **Spec in TypeScript** — `specs/Native<Name>.ts` (the folder named by `codegenConfig.jsSrcsDir`). The file name
   **must** start with `Native`; the interface **must** be named `Spec` and extend `TurboModule`; only
   Codegen-supported types (`string`, `number`, `boolean`, `Int32`/`Double`/`Float` from `CodegenTypes`,
   `Promise<T>`, typed object literals, `ReadonlyArray<T>`, callbacks, `UnsafeObject` as a last resort; no unions
   except string-literal ones, no generics beyond these):

   ```ts
   import type { TurboModule } from "react-native";
   import { TurboModuleRegistry } from "react-native";

   export interface Spec extends TurboModule {
     getBatteryLevel(): Promise<number>;
     formatBytes(bytes: number): string;
     readonly getConstants: () => { readonly model: string };
   }

   export default TurboModuleRegistry.getEnforcing<Spec>("NativeBatteryStatus");
   ```

   **The module name must not collide with one of React Native's own core specs** (`NativeDeviceInfo`,
   `NativeAppState`, … — the `Native*.js` files under `react-native/src/private/specs_DEPRECATED/modules/`): the
   Android C++ build then fails with `redefinition of 'Native…SpecJSI'` against
   `FBReactNativeSpec.h` (verified on RN 0.87). Give app modules a distinctive name (`NativeBatteryStatus`,
   `NativeOrdersStorage`) and grep `node_modules/react-native` for it first.

   This is the one place where a default export is required (Codegen reads it). Wrap it in a small, named-export
   TS facade (`src/native/batteryStatus.ts`) that validates results and is what the rest of the app imports — and what
   tests mock.
2. **`codegenConfig` in `package.json`** — `{ "name": "AppSpecs", "type": "modules" | "components" | "all",
   "jsSrcsDir": "specs", "android": { "javaPackageName": "com.<app>.specs" } }`, plus, for iOS app-level modules,
   `"ios": { "modulesProvider": { "NativeBatteryStatus": "RCTNativeBatteryStatus" } }`. Extend the existing block; don't
   create a second one.
3. **Android (Kotlin)** — `class NativeBatteryStatusModule(reactContext: ReactApplicationContext) :
   NativeBatteryStatusSpec(reactContext)` (the generated abstract class; `NAME` comes from it), plus a
   `BaseReactPackage` returning it from `getModule` and describing it in `getReactModuleInfoProvider`
   (`isTurboModule = true`), registered in `MainApplication.kt` inside `PackageList(this).packages.apply {
   add(NativeBatteryStatusPackage()) }`. Resolve promises exactly once; reject with a stable string code
   (`promise.reject("E_UNAVAILABLE", message, throwable)`); never block the JS thread with I/O.
4. **iOS (Obj-C++)** — `RCTNativeBatteryStatus.h/.mm` conforming to the generated `<NativeBatteryStatusSpec>` protocol
   (from `<AppSpecs/AppSpecs.h>`), with `getTurboModule:` returning
   `std::make_shared<facebook::react::NativeBatteryStatusSpecJSI>(params)` and `+ moduleName`. Swift is allowed for
   the logic, called from the `.mm` through an `@objc` class — the Turbo Module entry point itself stays Obj-C++.
   Add the files to the app target (`metro.md`) and note that `pod install` must re-run (Codegen runs then).
5. **Generated code is never edited or committed** — Android's lands in `android/app/build/generated/source/codegen`,
   iOS's in `ios/build/generated/ios` (Codegen during `pod install`). If the spec and the native class disagree, the
   *native build* fails, not `tsc` — keep method names, argument order, and nullability identical on all three sides.
6. **Fabric native component** — same pattern with `type: "components"`: a `<Name>NativeComponent.ts` spec using
   `codegenNativeComponent<NativeProps>("<Name>")` with `ViewProps`-extending props and `DirectEventHandler`/
   `BubblingEventHandler` events, a Kotlin `SimpleViewManager`/`ViewGroupManager` implementing the generated
   `<Name>ManagerInterface`, and an iOS `RCTViewComponentView` subclass. Only when the task asks for a native view.

## Expo module (expo, or metro with `expo-modules-core`)

- Layout from `create-expo-module --local`: `modules/<name>/expo-module.config.json` (platforms + module class names),
  `index.ts` (public TS API), `src/<Name>Module.ts` (`requireNativeModule<…>("<Name>")` from `expo` /
  `expo-modules-core`), `ios/<Name>Module.swift`, `android/src/main/java/…/<Name>Module.kt`. Autolinked — no
  `MainApplication`/Podfile edit.
- Native side uses the declarative DSL in **Swift and Kotlin** (no Obj-C++):

  ```swift
  public class DeviceInfoModule: Module {
    public func definition() -> ModuleDefinition {
      Name("DeviceInfo")
      Function("formatBytes") { (bytes: Double) -> String in ... }
      AsyncFunction("getBatteryLevel") { () -> Double in ... }   // throws → JS rejection
      Events("onChange")
    }
  }
  ```

  The Kotlin twin uses `Name(...)`, `Function(...)`, `AsyncFunction(...)` inside `override fun definition() =
  ModuleDefinition { ... }`. Throw `Exception`/`CodedException` subclasses with a stable code — they surface in JS
  as a rejected promise with `code`.
- Native views: `View(<Name>View::class) { Prop("…") { … } }` with an `ExpoView` subclass; JS side
  `requireNativeView`.
- Native config the module needs (permissions, plist keys) ships as the module's **config plugin**
  (`app.plugin.js`), so prebuild applies it — never by hand in `android/`/`ios/`.
- Type the JS facade: declare the module's TS interface (`declare class DeviceInfoModule extends NativeModule<Events>
  { formatBytes(bytes: number): string; getBatteryLevel(): Promise<number> }`), export named functions from
  `index.ts`, and give them TSDoc (`tsdoc.md`).

## Tests for each side

- **JS/TS side (always)** — unit-test the facade with the native module mocked at its boundary:
  `jest.mock("../specs/NativeBatteryStatus", () => ({ __esModule: true, default: { getBatteryLevel: jest.fn(),
  formatBytes: jest.fn(), getConstants: () => ({ model: "test" }) } }))`, or `jest.mock("expo-modules-core", …)` /
  mock the module's own `src/<Name>Module.ts` for an Expo module. Cover the facade's validation, error mapping
  (rejection code → typed `Error`), and the unsupported-platform path. These are what count toward the 80% gate.
- **Android native** — JUnit tests under `android/app/src/test/java/…` (or the Expo module's
  `android/src/test/`) for pure Kotlin logic extracted from the module class; the module class itself, which needs a
  `ReactApplicationContext`, is better kept thin. Run by the group skill (`./gradlew testDebugUnitTest` from
  `android/`).
- **iOS native** — XCTest cases in the app's test target for pure Swift logic, when the project has a test target;
  simulator-bound, so the group skill may report them as unverified on a machine without one.
- **End to end** — a Maestro flow (`.maestro/<feature>.yaml`) exercising the feature on a device when the project
  has Maestro (`testing.md`); written here, run by the group skill.
- Say in the report which sides got tests and which native changes need a rebuild (`pod install`, Gradle sync,
  development build) before anything can be observed.
