# Implement one plan task (React Native)

Carry out a single task's implementation, tests, and checkbox update in a React Native app — nothing else. This is
the narrowest execution unit for a `react-native`-tagged task in the `iru-code` pipeline:
`iru-react-native-code-one-task-group` calls it once per task in a bucket (possibly many at once, in parallel
agents), then runs license headers, TSDoc, Jest, coverage, ESLint/`tsc`/Prettier, any native build/test stage, and
the e2e flows once for the whole bucket.

What makes it different from `iru-typescript-code-one-task`, and why Step 1 is longer:

1. **Two toolchains own native code differently.** In an **expo** app `android/` and `ios/` are generated by
   `npx expo prebuild` — a hand edit there is silently lost, so native changes go through app config, config
   plugins, or a local Expo module. In a **metro** app (React Native Community CLI) they are committed source the
   task may have to edit, and both platforms must keep building. Expo also bundles with Metro under the hood; the
   name `metro` refers to the toolchain without the Expo framework, not to a different bundler.
2. **The testing library changed shape.** React Native Testing Library 14 made `render`, `fireEvent`, `renderHook`,
   and `act` async; a test written for the wrong major passes vacuously or fails confusingly. Step 1 pins it.
3. **Native changes can't ship over the air.** A change to native code, a config plugin, or a native dependency
   needs a new binary; the report says so, so the group skill and the user know what must be rebuilt.

It uses a medium model on purpose: the plan carries the hard reasoning; the React Native rules live in
`reference/`.

## Step 1 — Detect the project profile, then read only the reference material this task needs

Detect each of these once, from the app root (the directory whose `package.json` has `react-native`; in a
monorepo, the app package the task names). Don't guess any of them from memory.

1. **Toolchain** — the contract rule every React Native skill in this catalog uses:
   - `expo` in `package.json` `dependencies` → **expo**, even when `android/`/`ios/` directories exist (they are
     prebuild/CNG output). If `android/`/`ios/` are committed to git (`git ls-files android ios | head`) *and*
     nothing in the build regenerates them, note it — `reference/expo.md` treats that as an ambiguity to raise.
   - `react-native` in `dependencies` without `expo`, plus any of `metro.config.js`, committed `android/` + `ios/`,
     or `@react-native-community/cli` in `devDependencies` → **metro**.
   - Neither → not a React Native app; stop and report that the task was mis-routed (it belongs to another key).
2. **Versions**: `node -p "require('react-native/package.json').version"`, and for expo
   `node -p "require('expo/package.json').version"` (the major is the SDK) — fall back to the ranges in
   `package.json` when `node_modules` is absent and say so in Step 7. Note `react`'s version too.
3. **Routing**: expo — Expo Router (`expo-router` dependency, `main: "expo-router/entry"`), routes in `app/` or
   `src/app/` (whichever exists), `experiments.typedRoutes`; metro — React Navigation packages and whether the root
   navigator uses the static (`createStaticNavigation`) or dynamic (`<Stack.Navigator>`) API, or none yet.
4. **Tests**: the Jest preset (`jest-expo`/`jest-expo/<platform>` vs `@react-native/jest-preset`, or the legacy
   `react-native` preset) from `jest.config.*` or the `jest` key, where existing tests live (co-located vs
   `__tests__/`), and the installed **`@testing-library/react-native` major** (`node -p
   "require('@testing-library/react-native/package.json').version"`) — 14+ means async `render`/`fireEvent`. No Jest
   config at all → note it (a task asking for tests then has a blocker, Step 5).
5. **E2E**: `.maestro/` flows (Maestro) or `.detoxrc.*` + `e2e/` (Detox), or none.
6. **State and native libraries in play** (only those relevant to the task): server state (`@tanstack/react-query`,
   SWR, RTK Query, Apollo), store (Zustand, Redux Toolkit), storage (`@react-native-async-storage/async-storage`,
   `react-native-mmkv`, `expo-secure-store`, `react-native-keychain`, `expo-sqlite`), `react-native-reanimated`,
   `react-native-gesture-handler`, `react-native-webview`, `expo-modules-core` in a metro app, a `codegenConfig`
   block in `package.json`.
7. **Native layout (metro)**: `android/` Gradle DSL (Groovy `build.gradle` or Kotlin `.kts`), the app package under
   `android/app/src/main/java/`, `ios/<AppName>.xcworkspace`/scheme, `AppDelegate.swift` vs `.mm`.
8. **Package manager**: `packageManager` field or lockfile (`package-lock.json` → npm, `pnpm-lock.yaml` → pnpm,
   `yarn.lock` → yarn, `bun.lock` → bun).
9. **Agent guidance**: read the project's `AGENTS.md`/`CLAUDE.md` if present (the Expo SDK 57 template ships an
   `AGENTS.md` pointing at the SDK's versioned docs) and follow it where it is more specific than `reference/`.

Then read `reference/README.md` first — it is short and routes you to the rest — and only what it points at for this
task. The routing, restated:

| Read | When |
|---|---|
| `reference/mandatory-rules.md` | **Always**, and in full — it overrides "match the surrounding code". |
| `reference/code-style.md` | **Always.** |
| `reference/expo.md` | Toolchain is **expo** — always. |
| `reference/metro.md` | Toolchain is **metro** — always. |
| `reference/native-modules.md` | The task adds/changes native code, a Codegen spec, an Expo module, or a config plugin. |
| `reference/state-and-data.md` | State, hooks, context, server data, persistence, offline. |
| `reference/ui-and-platform.md` | Layout, styling, lists, images, animations, accessibility, platform-specific behaviour. |
| `reference/ui-contract.md` + `reference/ui-implementation.md` | The task adds or changes a screen, component, list or other UI — the catalog-wide UI contract and its React Native mapping (decomposition, composition, state/events, virtualized lists, UI tests, the UI gallery + screenshots, accessibility level). |
| `reference/testing.md` | The task writes or updates tests — nearly always. |
| `reference/security.md` | Auth/tokens, config values, sensitive storage, deep links/intents, WebViews, networking/TLS, logging, permissions. |
| `reference/tsdoc.md` | The task adds or changes an exported symbol. |

Exactly one toolchain file — never both. A one-line change inside an existing component is `mandatory-rules.md` +
`code-style.md` + the toolchain file + `testing.md`. Don't read the rest speculatively.

If `reference/` is missing (the skill directory was copied without it), proceed with this repository's own
`CLAUDE.md`/`AGENTS.md` conventions and the surrounding code's style — and, if `iru-typescript-code-one-task` is
installed, its `reference/code-style.md`/`testing.md`/`tsdoc.md` — and say so in Step 7; don't guess at what the
reference would have said.

## Step 2 — Re-check the current code state

Read the actual current content of the file(s) the task touches before editing — other tasks in the same bucket
may be landing concurrently, and "current code state" notes passed in may be stale. For a screen, also read the
navigator/layout that registers it and the feature modules it imports; for a native change, read both platforms'
existing counterparts (and, for expo, `app.json`/`app.config.*` and its `plugins`).

Note what the surrounding code already does about the things `reference/` has opinions on — file naming
(kebab-case vs PascalCase), styling approach, where server state lives, how tests render (async or not), how
native modules are wrapped. The reference is the default for new code; a file that consistently does something
else wins, and the divergence goes in Step 7 — except where `reference/mandatory-rules.md` says otherwise.

## Step 3 — Implement exactly what the task specifies

Apply the reference files Step 1 selected, plus this repository's own `CLAUDE.md`/`AGENTS.md` conventions where they
are more specific. Non-negotiable (each is a `mandatory-rules.md` rule, repeated because getting it wrong ships to
every installed copy of the app):

- **Toolchain boundaries.** expo: nothing under `android/`/`ios/` — native configuration via app config, a config
  plugin, or a local Expo module. metro: native edits on both platforms where the feature exists on both; new native
  files wired into the build (Gradle source set / Xcode target, `codegenConfig`, package registration). Never edit
  generated Codegen output, `Pods/`, or `.expo/`.
- **No new dependency (JS or native) and no build/config change the task didn't ask for** — otherwise that's a
  blocker to report (Step 5). Never touch version/build-number fields or `runtimeVersion`.
- **Full TSDoc** on every exported symbol (`@param`/`@returns`/`@throws`), props interfaces and hooks included.
- **No `any`, `readonly` by default, named exports** except the toolchain-required default exports (Expo Router
  route files, `App.tsx`, a Codegen spec's default export).
- **Security**: no secrets in the bundle/app config, tokens only in the keystore, deep-link params validated,
  WebView/`Linking` allow-lists.
- **UI**: accessible role + name on every interactive element, virtualized lists for unbounded data, safe-area
  insets from `react-native-safe-area-context`, effects that clean up.
- **UI work starts with the decomposition** (`reference/ui-contract.md` §2): before writing a screen or component,
  write its `Screen › Region › Component` tree (inputs, events, visual states, what it reuses — search
  `src/components/` and the feature folders first), then build leaves → composed components → screens → navigation
  per `reference/ui-implementation.md`: presentational components with a `Readonly` state prop and `on…` callbacks,
  the screen owning the view model hook, a `<Component>.fixtures.ts` per component, and `FlatList`/`SectionList` +
  a memoized item component for every data-driven collection. Include the tree in the Step 7 report.

Don't add anything the task didn't ask for — no speculative abstractions, no unrelated cleanup, no restyling, no
navigator restructure, no new state layer.

## Step 4 — Write or update the tests

Follow `reference/testing.md` and the existing tests next to the code: Jest under the detected preset, RNTL with the
API shape of the installed major (`await render(...)` on 14+), `userEvent` for interaction, `getByRole` with an
accessible name first, fake timers instead of sleeps, native modules and network mocked at their boundary. Cover the
new/changed behaviour, every documented `@throws`/rejection, loading/error/empty states, platform branches the task
adds, and validation of untrusted input. For native code, add the JS facade tests (always) and, where the logic
lives natively and the project has native test targets, JUnit/XCTest tests per `reference/native-modules.md`. Add or
extend a Maestro flow (or Detox test) only for a user-visible path the task adds, and only if the project already
has that e2e framework.

For UI work, follow `reference/ui-contract.md` §6–§8 as mapped in `reference/ui-implementation.md`: RNTL component
and screen tests over every fixture state (behaviour once, LTR light; events with their payloads; disabled states
silent; role/label queries), the component's/screen's entries in the UI gallery registry
(`src/dev/ui-gallery/registry.tsx`) plus a `.maestro/ui/<Id>.yaml` capture flow calling the
`.maestro/subflows/ui-capture.yaml` helper for each state × `.ui-quality.yml` direction × theme, `takeScreenshot`
steps in any flow the task adds, and code that passes `eslint-plugin-react-native-a11y` at the `.ui-quality.yml`
level. If the project has no gallery, deep-link scheme or `.maestro/` yet, write the RNTL tests and report the missing
capture infrastructure instead of inventing it (a scheme is a config change — Step 5). Detox projects use
`e2e/support/ui-screenshots.ts` instead of the subflow.

Do not run anything — not Jest, not `tsc`, not ESLint, not Gradle/CocoaPods/`xcodebuild`, not Metro, not
`expo prebuild`, not an e2e flow. `iru-react-native-code-one-task-group` does that once for the whole bucket, with the
e2e stage serialized behind the repository-wide `.integration-test.lock` — running a device flow from a parallel
task agent would collide with it.

## Step 5 — When to interrupt the user

Keep interruptions rare. Stop and use `AskUserQuestion` (or plain text if there's no real choice) only when:

- The task is ambiguous in a way that changes correctness or scope and can't be safely inferred (e.g. which
  platform(s) a native feature must support, what wins in an offline conflict).
- The task's approach is infeasible against the real code — it names a screen, route, module, or native class that
  doesn't exist, or asks for something the toolchain forbids (editing `ios/` in a CNG expo app, a legacy bridge
  module on the New Architecture). Name the rule; don't silently translate it into another approach unless the
  translation is mechanical and documented in `reference/` (then do it and report it).
- It needs a new dependency (JS or native), a config/build change, a new permission, or a new environment/config
  value the task didn't mention.
- The toolchain detection is genuinely ambiguous (an expo app with committed native directories and no prebuild in
  its pipeline; a monorepo where the task doesn't name the app).
- The change would extend an existing security defect (a token already kept in AsyncStorage that the task asks you
  to read from a new place).

Don't stop merely because the task is nontrivial. Don't report a task done to work around a blocker — report it
blocked (Step 7) with what was tried and why it failed. A conflict between `reference/` and the surrounding code is
not a reason to stop: follow the surrounding code (unless `mandatory-rules.md` forbids it) and report the
divergence.

## Step 6 — Check off this task's checkbox now

Unless this task stopped on a blocker, update `implementation_plan.md` at the repository root before reporting.
Re-read it fresh (sibling tasks may be editing it concurrently), find this task's own checkbox line by the exact text
passed in, flip `[ ]` to `[x]` for it and for every sub-task completed, and add a short note, e.g. `- [x] Task 2.
**Add `OrderRow` component** — implemented, tests added; group validation pending.` — the same "pending" wording
`iru-react-native-code-one-task-group` replaces once it has validated the bucket. Edit only this task's own line(s),
never surrounding lines or other tasks' checkboxes. If the task stopped on a blocker, leave its checkbox untouched.

## Step 7 — Report the outcome

Hand control back with a short summary:

- **The detected profile** — toolchain (`expo`/`metro`), React Native / Expo SDK / React versions, routing, Jest
  preset, RNTL major, e2e framework — and the reference files actually read.
- **The files touched**, grouped as JS/TS, native (`android/`, `ios/`, `modules/<name>/`), and config (`app.json`,
  `package.json` `codegenConfig`, plugins) — and **the tests added/updated** (Jest, native JUnit/XCTest, Maestro/Detox
  flows), none of them run.
- **For UI work**: the `Screen › Region › Component` decomposition (new vs reused, collection vs item), the UI tests
  added (RNTL component/screen tests, gallery registry entries, `.maestro/ui/` capture flows, flow captures) and the
  screenshot names they will produce (`<kind>/<Id>/<state>--<dir>--<theme>--<platform>`), plus any missing capture
  infrastructure.
- **Native impact**: which platform(s) changed natively, and what the group skill/user must do before it can be
  observed — `pod install`, a Gradle sync/build, a new development build, an `expo prebuild` check because a config
  plugin changed — and whether the change is OTA-compatible (EAS Update) or needs a new binary.
- **Whether this task stopped on a blocker** (Step 5), with enough detail for the caller to surface it.
- **Any deliberate deviation from `reference/`** — matching a file that uses another convention, a toolchain-required
  default export, a pre-existing `mandatory-rules.md` violation noticed but left alone — or that `reference/` was
  missing.

This skill never captures a quality baseline and never runs tests, coverage, linting, type-checking, native builds,
Metro, or e2e flows.
