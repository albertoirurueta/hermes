# Spring Boot rolling deployments — enable / disable / change

Switch **blue/green rolling deployments** on or off, or change their strategy, in a repository whose scaffold came from
`iru-setup-java-springboot`. This skill owns **one manifest block** (`deploy.rolling` in `springboot-stack.yml`) and
delegates every generated file to the sub-skills that already own them: it generates nothing itself.

What rolling deployments mean (same design as the sub-skills — **the workflow drives the shifting, the rollout state
lives in the cloud**): the new version ("green") deploys at 0 % traffic, is smoke-tested, then shifted per
`strategy` (`canary`/`linear` through `steps`, `blue-green` as one cutover, `rolling` as the runtime's native in-place
update with no traffic split), the old version ("blue") stays for rollback. `advance` decides who moves it forward:
`auto` (metric gate only), `manual` (a human through `promote.yml` for every step), `hybrid` (the gate must pass, then a
human confirms on `prod`; `dev` auto-advances; a failing gate rolls back automatically).

Five rules govern the skill:

1. **Never apply infrastructure.** This skill edits the manifest and runs generators. It never runs `tofu apply`,
   `tofu destroy`, `aws`/`gcloud`/`kubectl` mutations, or triggers a workflow. Reading is fine (`tofu output`, `gh`
   listing, `kubectl get`, `aws ... describe`).
2. **Never replace live-resource configuration unattended.** The sub-skills are run with update semantics
   (`on-existing: update`), never `replace`, unless the user explicitly picks Replace for a specific file.
3. **Never leave a rollout orphaned.** Changing the strategy or disabling while the cloud split is not 100 % stable
   stops the skill (Step 3).
4. **Never delete without asking.** `promote.yml` is a file this skill's sub-skill owns; removing it needs a confirmation.
5. **No credentials, ever.** Nothing here writes a secret into a file.

Agent dispatch: call the catalog agents as `subagent_type: "<agent-name>"` (for example `"iru-gate-runner"`) when installed under `.claude/agents/`, or as `"iru-core:<agent-name>"` when installed as a plugin — use whichever name appears in your available agent types. Every `subagent_type` below is written in the first form.

## Step 0 — Parse `args` and resolve the action

Parse `args` for `key: value` lines (the action word may arrive as the first line or as `action: enable|disable`):

```
action: enable
strategy: canary
advance: hybrid
steps: 10,50,100
bake-minutes: 10
stack-file: springboot-stack.yml
on-existing: update
```

`stack-file` defaults to `springboot-stack.yml`. `on-existing` (`ask`/`keep`/`update`/`replace`) defaults to
**`update`** here (unlike the sub-skills' default `ask`), because the point of this skill is to modify an existing
scaffold in place; it is forwarded to both sub-skills. If the manifest does not exist, stop: this skill needs a
`springboot-stack.yml` from `iru-setup-java-springboot` (offer to run it).

If there is no action, report the detected state (Step 1) and ask with `AskUserQuestion`: **Enable**, **Change
strategy / advance / steps** (only when currently enabled), **Disable** (only when currently enabled).

## Step 1 — Detect the setup state

Read, without changing anything:

- `springboot-stack.yml`: `deploy.rolling` (`enabled`, `strategy`, `advance`, `steps`, `bakeMinutes`), `ci.enabled`,
  `stack.cloud`, `project.language`/`buildTool`. **`ci.enabled: false` ⇒ stop for Enable**: rolling deployments are
  driven by the generated workflows; say so and offer to turn CI on through `iru-setup-java-springboot`. (Disable on a
  `ci: no` repository only edits the manifest.)
- `.github/workflows/deploy.yml`: *absent*, *single-job* (today's template), or *staged* (has a `deploy-green` job).
  `.github/workflows/promote.yml`: *absent* or *present*.
- `infra/`: whether `infra/envs/*` exists; which `rollout_*` outputs (`rollout_candidate_url`, `rollout_gate`,
  `rollout_alarm_names`, `rollout_target_groups`, `rollout_name`) appear in the `outputs.tf` files, and so which
  runtime (`cloudwatch` ⇒ ECS, `cloud-monitoring` ⇒ Cloud Run, `prometheus` ⇒ Kubernetes) the rollout would use.

Print a short **Setup mode** statement before asking anything, in the style of the other setup skills: *enabling
rolling deployments* / *disabling* / *changing from <old> to <new>*, plus an inventory marked absent / present /
partial: manifest block, `deploy.yml` (single-job / staged), `promote.yml`, rollout infrastructure in `infra/`. A
mismatch between the manifest and the files (manifest says enabled but `deploy.yml` is single-job, or the reverse) is
reported as **drift** — both sub-skills fix it on this run.

## Step 2 — Enable or change: resolve the choices

Ask only what `args` did not supply, with `AskUserQuestion` (max 4 questions per call), using **exactly the
orchestrator's defaults** (`iru-setup-java-springboot` Step 3c):

1. **Strategy** — **Canary (Recommended)**, **Blue/green** (`steps: [100]`), **Linear**, **Rolling** (native in-place
   update; no `promote.yml`, `advance` limited to `auto`, weaker rollback).
2. **Advancement** (skipped for `rolling`, which resolves to `auto`) — **Hybrid (Recommended)**, **Auto**, **Manual**.
3. **Steps and soak** — **Use defaults (Recommended)** (`[10, 50, 100]` and `bakeMinutes: 10`; `[100]` for blue/green;
   none for rolling) or **Customize**.

Validate as the orchestrator does: `steps` strictly ascending integers in 1–100 ending in 100, `blue-green` is exactly
`[100]`, `rolling` with `manual`/`hybrid` is contradictory (ask which to change), and on ECS the strategies other than
`rolling` need an ALB (the platform skill flags and stops if there is none — relay that, do not work around it).

**Change** (already enabled): if the new `strategy`, `advance` or `steps` differ, run the in-progress check (Step 3)
first, because the running rollout was created with the old shape.

Then update the manifest — edit **only** the `deploy.rolling` block, keeping every comment and key around it:

```yaml
deploy:
  rolling:
    enabled: true
    strategy: canary
    advance: hybrid
    steps: [10, 50, 100]
    bakeMinutes: 10
```

Show the user the diff of the manifest and get a yes before writing it. Then run the sub-skills (Step 4).

## Step 3 — The in-progress check (Disable, and Change of shape)

A rollout is **in progress** when the cloud split is not 100 % on one version. Check it read-only, per environment
under `infra/envs/*`, from the cloud (the rollout state is never stored in GitHub):

- ECS: the production ALB listener's weights are not 100/0 (`aws elbv2 describe-listeners`), or the listener carries a
  `rollout-candidate` tag (`aws elbv2 describe-tags`).
- Cloud Run: `gcloud run services describe <service> --region <region> --format=json` shows a `candidate`-tagged
  traffic entry, or traffic split across revisions.
- Kubernetes: `kubectl get rollout <rollout_name> -n <namespace> -o json` is `Paused`/`Progressing` before its last step.

Needs cloud credentials the user already has locally; if the environment cannot be queried (no CLI, no login, never
deployed) say **"could not verify"** and ask the user to confirm there is no rollout in progress — never assume. If
any environment has one, **refuse**, name the environment and its current split, and tell the user to finish it first
(`promote.yml` with `next`, `rollback` or `abort`), then re-run this skill. Do not roll anything back yourself.

## Step 4 — Run the sub-skills

Delegate each to the `iru-isolated-skill-executor` agent, in this order (platform first so the `rollout_*` outputs the
workflows consume exist), letting their `AskUserQuestion`s through to the user:

```
Agent({
  description: "Update rolling-deployment infrastructure",
  subagent_type: "iru-isolated-skill-executor",
  prompt: "Invoke Skill({skill: \"iru-setup-java-springboot-platform\", args: \"stack-file: springboot-stack.yml\\n
    mode: existing\\non-existing: update\\nrolling: <yes|no>\\ndeployment-strategy: <strategy>\\nadvance: <advance>\\n
    steps: <comma list>\\nbake-minutes: <n>\"}). It must NOT run tofu apply or destroy; let any AskUserQuestion
    through to the user. Report back: per infra file group created/updated/kept, the rollout resources and rollout_*
    outputs, any prerequisite or cost note, and whether tofu validate passed.",
  run_in_background: false
})
Agent({
  description: "Update rolling-deployment workflows",
  subagent_type: "iru-isolated-skill-executor",
  prompt: "Invoke Skill({skill: \"iru-setup-java-springboot-github-workflows\", args: \"stack-file: springboot-stack.yml\\n
    mode: existing\\non-existing: update\\nrolling: <yes|no>\\ndeployment-strategy: <strategy>\\nadvance: <advance>\\n
    steps: <comma list>\\nbake-minutes: <n>\"}). Let any AskUserQuestion through to the user. Report back: the action
    per workflow file (deploy.yml, promote.yml, undeploy.yml, build.yml, security.yml), the new environment variables
    required, and anything it could not verify.",
  run_in_background: false
})
```

Rules for the runs:

- **Enable / Change** — `rolling: yes` with the resolved values. `on-existing: update` merges the staged `deploy.yml`
  and the new `promote.yml`; an existing `deploy.yml` customization survives where the sub-skill does not own it.
- **Never pass `replace`** for the platform skill. If the platform sub-skill finds a file it cannot merge safely
  (it manages live resources), it asks the user — do not answer on their behalf.
- When the user chose **Keep as is** for a file inside a sub-skill, respect it and report the resulting drift.
- If a sub-skill reports it **stopped** (e.g. an ECS service without an ALB cannot do `canary`), stop the whole run, leave
  the manifest edit in place only if the user wants to keep it, and say what remains inconsistent.

## Step 5 — Disable

Only after the in-progress check passed (Step 3) and the user confirmed. Disabling is the reverse of enabling, but the
**infrastructure side is deliberately left alone**:

1. Set `deploy.rolling.enabled: false` in the manifest (keep `strategy`, `advance`, `steps`, `bakeMinutes` so
   re-enabling remembers them); show the diff and get a yes first.
2. Run `iru-setup-java-springboot-github-workflows` with `rolling: no` and `on-existing: update` (Step 4's prompt):
   it restores today's single-job `deploy.yml` template and reports `promote.yml` as stale.
3. **Remove `promote.yml` — after an explicit confirmation**, because it is a file the workflows skill owns and
   that the user may have customized. Ask with `AskUserQuestion`: **Remove (Recommended)** / **Keep it**. Removing
   means deleting that one tracked file in the working tree (it stays recoverable from git history); nothing else is
   deleted. Never remove it silently, and never remove anything else.
4. Run `iru-setup-java-springboot-platform` with `rolling: no` **only if the user asks** — it would stop generating
   the rollout resources but must not remove existing ones; by default skip it.
5. **Warn about the leftover infrastructure**: the second target group / ECS slot service and test listener,
   the Cloud Run `traffic` pinning and tags, the Argo `Rollout`/`AnalysisTemplate`/Helm release, the alarms, remain
   in `infra/` and in the cloud (and keep costing money — the idle capacity is scaled to zero but the load balancer
   resources and alarms are not free). Removing them is a **reviewed `tofu plan` followed by an `apply` by the user**;
   this skill never does it, and the single-job `deploy.yml` will keep working against the slot-based ECS service
   only if the platform skill's non-rolling shape is restored first — say so plainly.

## Step 6 — Report

Summarize:

- **Mode**: enabled / disabled / changed (old → new), or "no change" with the reason.
- The final `deploy.rolling` values (strategy, advance, steps, bakeMinutes) and the runtime they apply to.
- **Per file action**: `springboot-stack.yml` (updated), `deploy.yml` (updated / replaced / kept as is, single-job ↔
  staged), `promote.yml` (**created / updated / replaced / kept as is / removed / not generated**), `undeploy.yml`,
  and the `infra/` file groups (created / updated / kept as is), as reported by the sub-skills.
- **Manual follow-ups**, as applicable: the new environment variables to set (`ECS_CLUSTER`, `ECS_SERVICE`,
  `CLOUD_RUN_SERVICE`, `EKS_CLUSTER_NAME`/`GKE_CLUSTER_NAME`, `K8S_NAMESPACE`); review and run `tofu plan` / `apply`
  yourself for the new rollout resources (this skill did not); tune the alarm / Monitoring thresholds; the
  deployment-branch rule on `prod`; the **"who may promote" finding** (`promote.yml` can be dispatched by anyone with
  repository write access; required reviewers on private repositories need GitHub Enterprise); the cost note
  (blue/green temporarily doubles capacity); after Disable, the leftover rollout infrastructure and the reviewed
  `tofu plan` that removes it; and the first real exercise — a `dev` deploy, one `promote`, one deliberate `rollback`.
- Anything unverified (live cloud behaviour no local check can prove) or any sub-skill that stopped.
